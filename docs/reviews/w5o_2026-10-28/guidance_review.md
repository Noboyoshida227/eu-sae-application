## Conclusion

The main guidelines, methodology mapping, MSE note and release instructions provide unusually extensive disclosure of extensions and remaining validation limits. The model equations and MCPE change identity agree with the original manuscript. They are not a literal reproduction of its workflow, and several standalone documents retain incorrect or stale explanations. Documentation existence does not establish statistical adequacy of the national-correlation approximation, the fixed variance threshold, boundary inference, or pointwise headline counts across many areas.

## Confirmed documentation findings

1. **P2 — The current sampling-covariance note still gives the retired `sm_out` rule.** `docs/guidance/Technical notes/Note on Estimating the Sampling-Error Covariance Matrix (revised).docx`, section 8, says `sm_out` replaces near-zero variances **or variances far above the smoothed value**. Current code retains every finite direct variance at least 0.001 (`R/variance_policy.R`, used in `scripts/01_ufh.R:981` and `scripts/02_mfh.R:883-884`). The guidelines explicitly supersede the old description in Annex G.8, and section 7.9 correctly says large variances are not replaced. Thus the departure is disclosed, but an analyst consulting the standalone technical note will receive the wrong rule. Replace the quoted rule and all “outlier-smoothed” explanations that imply upper-tail replacement; state the scale and strict threshold. The code comment at `scripts/02_mfh.R:888` also incorrectly says upper-tail trimming is what `sm_out` is for.

2. **P2 — Guidelines promise an obsolete benchmark fallback.** Guidelines section 7.12, PDF p52, says a missing target/model aggregate or near-zero aggregate causes the ratio factor to be set to 1, so the target may not be met. Current `sae_ufh_ratio_benchmark` stops for nonfinite target/average and for zero mean with nonzero target (`scripts/ufh_functions.R:2235-2240`); MFH does the same (`scripts/bench_regional_mfh.R:70,83`). For the zero-target/zero-aggregate case, MFH uses factor 1, while UFH sets group predictions to zero and records an undefined ratio. Describe current failure and reporting behavior, including any pipeline-level unavailable-benchmark status, instead of the retired silent fallback.

3. **P2 — Ratio benchmarking does not guarantee nonnegative rates.** MSE note Part I says the ratio form keeps rates nonnegative. Guidelines section 7.12 has the same unconditional purpose statement; the following paragraph correctly narrows this to a **positive factor applied to already nonnegative estimates** and notes the upper bound is not preserved. The allowed identity-scale Gaussian fits can produce negative predictions. Reproduction verified by uncertainty reviewer: `sae_ufh_ratio_benchmark(c(-.1,.3), c(.1,.3), c('all','all'), c(1,1))` returns `c(-.2,.6)`; MFH imposes no positivity restriction either. Qualify the guarantee in every standalone note, and require checking both lower and upper bounds for poverty estimates. This is a limitation/documentation error, not incorrect ratio arithmetic.

4. **P2 — The main covariance explanation treats a model assumption as a universal design fact.** Guidelines section 8.7, PDF p59, says reusing PSUs makes direct estimates positively correlated whenever reused. Annex G.8 already states a cluster-model condition; preserve it rather than treating it as an unconditional claim. A persistent positive cluster effect is one model that yields that result; actual covariance depends on the design, population evolution and overlap. The companion sampling note itself supplies the correct qualification: magnitude and sign depend on actual design/population and PSU reuse alone is not a covariance estimate. Rewrite the main guidance conditionally and retain empirical design-covariance/sensitivity checks. The same note's assertion that welfare intra-PSU correlation is necessarily “large” needs application evidence rather than a universal claim.

5. **P2 — The two-year comparison table softens the manuscript's multiplicity recommendation.** Guidelines Annex H says the paper merely “warns” about multiple testing. Original manuscript p37 accepts individual-area comparisons, explains Bonferroni `alpha/D` for familywise control, then advises against many-area testing because power becomes poor. The reporting departure is the prominence of pointwise counts across areas; Bonferroni output already exists. w5o retains pointwise primary colors/counts and uses BH/Bonferroni as sensitivity outputs. This choice is disclosed in guidelines section 8.12 and Annex H.4, the README and methodology mapping, but prominent pointwise counts go beyond the paper's individual-area emphasis. Describe the difference explicitly. Pointwise intervals are defensible for independently prespecified individual areas; they do not justify an overall family of “significantly changed” areas. BH controls a different error criterion and depends on its assumptions; it does not repair invalid boundary p-values.

6. **P3 — The w5n sampling note has not been updated for person-row weights.** Its section 12 unconditionally gives `population_weight = weight × household size`; section 8 describes `weights = ~weight`. w5o uses weight alone for person rows, and weight × size for household rows. The current guidelines and section 4.6, README, download instructions and Guide 2 p8 correctly explain the distinction. Add that distinction to the standalone note and use the actual `population_weight` variable name. This stale note can recreate the weighting error that w5o was designed to fix.

## Proposed replacement wording

- **Sampling-covariance note §8:** “`sm_out` retains a finite direct variance at least 0.001 and replaces a missing, nonfinite or smaller value with its GVF prediction. It does not replace large variances. The threshold is an application policy; in log-mean models it is applied on the log-mean variance scale. `sm_all` replaces all variances; `direct` retains raw variances subject to explicit safety backfills.”
- **Guidelines §7.12:** “Benchmarking requires finite estimates, targets and usable population totals for every requested group and year. A zero model aggregate can only meet a zero target; a nonzero target with zero model aggregate is an error. When the pipeline cannot produce a requested benchmarked result, inspect the recorded benchmark status rather than assuming a unit adjustment was applied.”
- **MSE note Part I / guidelines:** “A positive ratio factor preserves nonnegativity of predictions that are already nonnegative and preserves their ordering within the group. It does not repair negative predictions or guarantee an upper bound of one. Review the range of all poverty estimates before reporting.”
- **Guidelines §8.7, baseline p59 (retain the existing Annex G.8 condition):** “Under a persistent positive cluster-effect model, reused PSUs can induce positive cross-year covariance even when different households are sampled. The actual covariance depends on the joint survey design, population and overlap; PSU reuse alone does not establish its magnitude or sign. Estimate it using the correctly specified joint design and assess sensitivity to the working covariance choice.”
- **Guidelines Annex H:** “Molina and Romero (2025, p37) recommend Bonferroni correction for familywide testing across areas and caution that testing many areas may have little power. The Workbench instead retains pointwise primary displays and supplies BH and Bonferroni sensitivity results. This is an explicit reporting-policy departure. Pointwise results support prespecified individual-area statements; any familywide conclusion must use its declared multiplicity rule and acknowledge the validity limits of the underlying p-values.”
- **Sampling-covariance note §12 and §8:** “The survey design uses `population_weight`: survey weight multiplied by household size for one-row-per-household data, or survey weight alone for one-row-per-person data. The declared row unit, PSU identifiers and optional strata must match the survey design.”
- **Alignment matrix / guidelines Annex H GVF row:** “Relative to the paper's `exp(fitted log variance)` illustration, the implementation uses `exp(predicted log variance + residual variance/2)` (`scripts/ufh_functions.R:65-70`). This is a lognormal conditional-mean correction requiring suitable log-GVF residual assumptions; its adequacy should be checked rather than described as universally unbiased.”

## Validation interpretation

The current QER material accurately distinguishes exact-parameter checks, installed-package checks and fitted-model coverage. The 2,100-outer-sample MFH2 experiment supports only its specified Gaussian/lognormal scenarios with known sampling covariances and fixed covariates. It excludes full complex-survey sampling, estimated GVFs/covariances, model selection and benchmarking. Reported low-signal absolute-change coverage of 87.40% and 65.21% among correlation-limit original fits is direct evidence against unqualified nominal-95% claims in those scenarios. More bootstrap draws address Monte Carlo noise, not this limitation.

The four technical notes are dated w5n and intentionally retain theoretical/historical material. The covariance-prediction paper explicitly says its missing-area theory is not current pipeline capability and its historical simulations do not validate the present bootstrap. That distinction is appropriate; the older implementation paragraphs above still need repair.

## Instruction checks and limitations

Reviewed current English install/start guide, running guide, estimation guide, download instructions, README_WIZARD, release notice, methodology mapping, revision status and QER/MCPE summaries. Guide 3 p7, p18 and p20 and the matching Polish/Greek sections agree on MFH2/default 500, identity FGT1/2, log arithmetic means, distinct UFH/MFH corrections, boundary caveats and noncertified coverage. Guide 2's household/person weighting, PSU consistency and benchmark choices agree across inspected translated sections. The full translated text was extracted; this is a focused methodological consistency check, not a certified linguistic or visual-layout review of every translation. No source documentation or production code was edited by this review.
